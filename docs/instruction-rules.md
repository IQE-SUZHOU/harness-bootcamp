# 指令文件的膨胀防护规则

## 为什么"再加一条规则"是止痛药也是毒药

agent 犯错 → 加条规则 → 暂时管用 → 再犯另一个错 → 再加一条。三个月后入口文件 600 行，
后果是四个：上下文预算被吃掉（10-20K tokens）、中间迷失（关键约束落在中段遵循率骤降）、
优先级冲突（红线和建议长得一模一样）、维护衰减加矛盾累积（过时规则没人删，互相矛盾随机遵循）。

## 本仓库的硬性阈值

| 阈值 | 值 | 由谁检查 |
|------|----|----------|
| 入口文件行数 | ≤ 100 | `scripts/check_contract.py` |
| 入口文件下限 | ≥ 30 | 同上，防桩文件 |
| 硬约束条数 | ≤ 15 | 同上 |
| 专题文档行数 | 20 - 150 | 同上 |
| 路由条目下限 | ≥ 5 | 同上，防目录页不履职 |
| 中部高风险区 | 全文 40%-65% 行区间 | 告警，不判失败 |

## 拆分判定

一条规则想进 `AGENTS.md` 之前，先问三个问题：

1. 是否每次任务都必须遵守？不是 → 放 `docs/` 专题文档，入口只留一行指针加适用条件。
2. 是否可以用命令检查？能 → 写进门禁（`scripts/check_contract.py`），指令里不用重复。
3. 是否与已有条目矛盾或重复？是 → 删旧的，不要并列共存。

放不进专题文档又必须留在入口文件的，只放文件顶部或底部，不放中间。

## 每条规则带三个元数据

在 `docs/` 里展开规则时，每条必须标明：

- 来源：为什么加这条（哪次失败、哪一层的归因）
- 适用条件：什么时候需要读它（改哪类文件时必读）
- 过期条件：什么情况下可以删掉它

三者缺一，规则就进入待审计状态。像管理依赖一样管理指令，用不上的依赖只会拖慢系统。

## 信噪比审计（L04 练习 1）

1. 列出入口文件全部条目。
2. 选 5 类常见任务（改 bug、加测试、改文档、调门禁、跨会话恢复）。
3. 逐条标注是否与该任务相关，算出每类的信噪比。
4. 对多数任务都是噪声的条目，移入专题文档或直接删除。

## 拆分效果必须实测

拆完之后拿同一组任务（≥5 个）对比拆分前后的成功率与耗时。文件变短不等于效果必然变好：
仓库级上下文文件本身会增加推理成本，需要在真实任务上验证，不能只看行数下降。
