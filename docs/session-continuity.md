# 跨会话连续性协议

## 上班（`make start`）

1. 读 `PROGRESS.md`：当前状态（commit + 测试通过率）、进行中、已知问题、下一步。
2. 读 `DECISIONS.md`：只看带日期的标题列表，需要细节时读对应小节。
3. 跑 `make check` 确认仓库处于一致状态；不过就不要开工，先修复。
4. 从「下一步」第一条开始，并把它在 `feature_list.json` 里标为 `active`（WIP=1）。

## 下班（`make finish`）

1. 更新 `PROGRESS.md` 六个小节，「本次会话交接」必须写：做了什么 / 为什么 / 试过并放弃的方案。
2. 新决策追加到 `DECISIONS.md`，格式：日期 + 标题 + 原因 + 否决方案 + 约束。
3. 跑 `make check`；不过就不允许把任何功能项写成 passing。
4. 提交已完成的工作，提交后把 `PROGRESS.md` 的 commit 更新为新 HEAD。

## 什么时候必须交接

- 上下文需求超过窗口 60%，或任务预计跨会话。
- 30 分钟内的短任务直接在会话内做完，不要为它建工件。
- 感觉要"赶紧收尾"时立刻交接：那是上下文焦虑的信号，此时做的决策质量最差。

## 压缩还是重置

| 策略 | 保留 | 丢失 | 适用 |
|------|------|------|------|
| 压缩 | 连续性、"是什么" | 决策的"为什么"；且不消除焦虑 | 任务接近完成、工件已完备 |
| 重置 | 干净心理状态 | 依赖工件完备性，漏写就在错方向浪费 | 工件齐备且任务还长 |

按目标模型选择，不能套通用模板：有的模型焦虑严重，压缩单独不够用，必须重置；
换一类模型该现象明显减弱，靠压缩即可。切换模型时，这一项要重新评估。

## 重建成本

指标：新会话仅凭 `PROGRESS.md` 恢复到"可以动手"所需读入的 token。
`scripts/audit_score.py` 用字符数除以 4 粗估，预算上限 1500 tokens；超限说明进度文件写成了流水账。
度量方法（L05 练习 1）：同一个任务跑 3 个会话，分别在有无进度文件两种条件下记录恢复开销，差值即工件的价值。

## 最小交接模板

见 `session-handoff.md`，四个必填字段：仓库状态（commit hash）、运行时状态（测试通过率）、
阻塞项、下一步行动。新会话只凭这四条必须能开工；出现歧义就把歧义点写进模板再迭代。

## 漂移

每次会话边界都引入理解与仓库实际状态的偏差，不控制会越漂越远。三个抑制手段：
git 检查点（原子提交，一个逻辑操作一次）、一致性谓词（`make check`）、
决策日志（否决过的方案不能被重新"优化"回来）。
