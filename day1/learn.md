## 1. 今天的核心论点

**模型能力强 ≠ 执行可靠。**

课程（lecture-01 *Why Capable Agents Still Fail*）的结论：同一个模型，裸跑时会出现能力鸿沟、验证缺口、发散执行——问题不在模型，在 Harness（输入结构 + 约束 + 验证）。所以 Agent 干不好，第一反应应该是"修 Harness"，而不是"换个模型"或"换个提示词话术"。

## 2. AGENTS.md 4 要素（记忆锚点）

1. **项目是什么** —— 背景与目标，一句话让 Agent 冷启动
2. **环境怎么跑** —— 依赖、安装、常用命令（尤其是**唯一的验证命令**）
3. **约束是什么** —— 不做清单，明确边界
4. **怎么算完成** —— 可执行的验证方式，不是"感觉做完了"

常见误区：写成愿望清单、不写验证方式、scope 不设边界。

## 3. Demo 设计与实现过程（day1/practice）

### 3.1 设计思路

课程 project-01 的原型是"Electron 壳子裸跑 vs 带 Harness 跑"。我们没有照搬，理由：Electron 环境重、启动慢，不适合 25 分钟现场演示。改用测试团队最熟悉的形态——**一个埋了 3 处 bug 的 pytest 项目**，任务只有一句话："让 pytest 全绿"。

对照实验设计：同一句提示词跑两轮，唯一变量是 AGENTS.md 是否在场。

| | Round 1 裸跑 | Round 2 带 Harness |
|---|---|---|
| 前置 | `mv AGENTS.md AGENTS.md.off` | AGENTS.md 在位 |
| 提示词 | "这个 repo 里的测试跑不过，帮我把代码修好。" | 同一句 |
| 演示人 | 任何人 | **不是写 AGENTS.md 的人**（考核要求） |

### 3.2 3 个 bug 与概念的映射

每个 bug 都不是随便埋的，各对应 Day 1 一个概念：

| # | Bug | 对应概念 | 裸跑 Agent 的典型翻车 |
|---|---|---|---|
| 1 | `from dateutil import parser`（未声明的第三方依赖） | **不做清单**（只允许标准库） | 直接 `pip install python-dateutil`，污染环境 |
| 2 | `SEVERITY_MAP["ERROR"] = "info"` | **可验证的完成标准**（测试钉死行为） | 想改测试"让通过"，或糊弄语义 |
| 3 | `TIMESTAMP_FORMAT` 用 `/` 分隔（日志实际是 `-`） | **环境事实要写准** | 凭猜测反复试格式，多次重试 |

彩蛋：正确修法是把 `parse_timestamp` 改用标准库 `datetime.strptime`，**一处修复同时消掉 bug 1 和 3**——AGENTS.md 里"只允许标准库"的约束反而把 Agent 推向了更优解。约束不是限制，是路标。

### 3.3 实现过程

1. 先写测试（9 个用例）——需求即测试，这也是仓库想传达的世界观
2. **先在临时副本上写修复版跑通全部 9 个用例**，保证 demo 可解（不能给一个解不出来的题）
3. 再把 3 个 bug 埋回源码，确认埋 bug 版在 collection 阶段就按设计报 `ModuleNotFoundError: dateutil`（陷阱触发点正确）
4. AGENTS.md 按 4 要素写，验证命令唯一：`python -m pytest tests/ -v`；"怎么算完成"写死两条：9 用例全绿 + 没动 tests/ 没加依赖

过程中修掉的一个小错：初版文档写"10 个用例"，实际 9 个——完成标准里的数字必须和现实一致，否则 Agent 会拿它当验证依据对不上号。

## 5. 业务映射（整组讨论）

我们的测试脚本 / 部署文档里，候选改写成 AGENTS.md 的对象：
- 队列机冒烟测试的执行手册（环境、命令、判 PASS 标准）

共同点：都是"给新手的一步步说明"——AGENTS.md 就是写给 Agent 的新手手册。
